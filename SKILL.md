# DETERMINISTIC_CALCULATION_SKILL v0.1

## 1. Назначение

Этот skill (навык) задаёт правило обработки математических расчётов внутри обычных ответов, статей, отчётов, таблиц, сравнений, объяснений и других пользовательских текстов.

Главный принцип: LLM (языковая модель) пишет текст, но не является источником числового результата, если этот результат требует вычисления. Если число нужно посчитать, LLM должна передать выражение в детерминированный расчётный механизм, получить результат и затем вставить рассчитанное число в ответ.

Контрольное правило:

```text
LLM_WRITES_TEXT=yes
LLM_AS_NUMERIC_SOURCE=no
CALCULATION_DELEGATION_REQUIRED=when_numeric_result_requires_calculation
```

## 2. Когда включать skill

Включать этот skill (навык), если задача содержит или подразумевает математическую операцию, числовое преобразование или вычисляемое значение.

Триггеры:

- арифметика: сложение, вычитание, умножение, деление;
- проценты, доли, отношения, пропорции, темпы роста, маржа;
- степени, корни, модуль, остаток от деления;
- логарифмы, экспоненты, научная запись чисел;
- тригонометрические функции: sin, cos, tan, asin, acos, atan;
- гиперболические функции: sinh, cosh, tanh и обратные функции;
- факториалы, перестановки, сочетания;
- округление, значащие цифры, допуски, точность;
- формулы с одним или несколькими шагами;
- конвертация единиц, расчёты дат/времени, валютная арифметика;
- табличные расчёты, суммы, средние, score (баллы), рейтинги;
- числовое сравнение: больше/меньше, min/max, проверка порогов;
- операции уровня engineering calculator (инженерного калькулятора), а не только четыре базовые арифметические операции.

Не включать skill для чисто текстовых, творческих, стилистических или оценочных задач, если внутри них не требуется вычисляемое число.

## 3. Правило делегирования расчёта

Если ассистент обнаруживает, что для корректного ответа нужен вычисляемый числовой результат, он не должен получать это число как вероятное продолжение текста.

Обязательный процесс:

1. Найти выражение, формулу, функцию, табличную операцию или числовую зависимость.
2. Нормализовать числа, обозначения, единицы измерения и допущения.
3. Передать выражение в доступный детерминированный расчётный механизм.
4. Получить вычисленный результат.
5. Вставить вычисленный результат в пользовательский текст.

Допустимые расчётные механизмы:

- Python (Питон);
- calculator (калькулятор);
- Data Analysis (анализ данных) / code execution (выполнение кода);
- spreadsheet / XLSX (таблица Excel) с формулами;
- специализированная математическая библиотека;
- формальный пошаговый алгоритм, если внешний инструмент недоступен.

Если внешний расчётный инструмент недоступен, ассистент может выполнить расчёт пошагово, но должен использовать формальный алгоритм, проверки области допустимых значений и проверку результата. Нельзя считать результат «догадкой LLM».

Нельзя писать или подразумевать, что был использован Python, calculator, Data Analysis или XLSX, если соответствующий инструмент фактически не использовался.

## 4. Нормализация входных данных

Перед расчётом проверить и нормализовать входные данные.

Проверить:

- числовую локаль: `1,800` может означать `1800` или `1,800` в зависимости от контекста;
- десятичный и разрядный разделитель;
- единицы измерения;
- валюты и дату курса, если нужна валютная конвертация;
- часовой пояс и календарные правила для расчётов дат/времени;
- знак числа и направление операции;
- скобки и приоритет операций;
- константы: pi, e, g, налоговая ставка, коэффициент пересчёта;
- требуемый вид результата: точный, десятичный, округлённый, приближённый или символьный.

Если числовая локаль неоднозначна и влияет на результат, ассистент должен остановиться или запросить уточнение.

Контрольное правило:

```text
CHECK_NUMERIC_LOCALE=when_ambiguous_or_scale_suspicious
RAW_VALUE_REQUIRED=when_locale_or_scale_risk_exists
```

## 5. Проверки для инженерных функций

Для функций сложнее базовой арифметики до расчёта выполнить проверки режима и области допустимых значений.

Обязательные проверки:

- деление на ноль недопустимо;
- корень чётной степени из отрицательного числа требует complex mode (режима комплексных чисел) или должен быть остановлен;
- аргумент логарифма в real mode (режиме действительных чисел) должен быть положительным;
- аргументы `asin` и `acos` в real mode должны быть в диапазоне `[-1, 1]`;
- `tan` не определён в точках 90° + 180° * k или `pi/2 + pi * k`;
- факториал требует неотрицательное целое число, если явно не задана интерпретация через gamma function (гамма-функцию);
- матричные и векторные операции требуют совместимых размерностей;
- степени с дробным показателем могут требовать уточнения real/complex mode;
- тригонометрические функции требуют явного angle mode (режима углов), если режим влияет на результат.

Правило режима углов:

```text
ANGLE_MODE_REQUIRED=for_trigonometric_functions
ANGLE_MODE_VALUES=degrees|radians
IF_ANGLE_MODE_AMBIGUOUS=ask_or_stop
```

## 6. Точность и округление

Не округлять промежуточные значения, если пользователь прямо не попросил об этом или метод не требует заранее заданной точности.

Правила:

- сохранять доступную точность на промежуточных шагах;
- округлять только финальный результат, если нет иной команды;
- если пользователь указал точность — использовать её;
- если точность не указана — выбрать разумную точность отображения по контексту;
- помечать приближение только если оно существенно;
- сохранять точную форму там, где это уместно: например `sqrt(2)` или `pi/3`, а десятичное приближение давать только при необходимости.

Контрольное правило:

```text
INTERMEDIATE_ROUNDING=forbidden_unless_requested
FINAL_ROUNDING=explicit_or_contextual
```

## 7. Политика вывода

Расчётный механизм является внутренним. Видимый ответ должен соответствовать задаче пользователя.

Формула, подстановка и проверка не являются обязательными в основном тексте. Показывать их или не показывать — решение ассистента по задаче, жанру и запросу пользователя.

Показывать механику расчёта, если:

- пользователь просит показать расчёт;
- задача является математическим решением, аудитом, проверкой или отладкой;
- формула повышает понятность;
- результат чувствителен к допущениям, единицам, точности или округлению.

Не показывать механику расчёта, если:

- пользователь пишет статью, отчёт, письмо, презентацию или связный текст, где нужно только итоговое число;
- формула перегружает текст;
- пользователь просит чистовой текст без технической трассировки.

Пример внутреннего расчёта:

```text
1000 / 10 / 5 = 20
```

Допустимый видимый текст без формулы:

```text
1000 тонн груза перевозится 10 грузовиками грузоподъёмностью 5 тонн. Каждый грузовик делает по 20 рейсов.
```

Допустимый видимый текст с формулой:

```text
1000 / 10 / 5 = 20, значит каждый грузовик делает по 20 рейсов.
```

Оба варианта допустимы. Обязательное требование не в том, чтобы формула была видна, а в том, чтобы значение `20` было получено детерминированным расчётом, а не LLM-предсказанием.

## 8. Политика диагностики

Если проблем нет, диагностику не выводить.

Диагностика нужна только для проблем, неоднозначностей или заблокированных расчётов.

Триггеры диагностики:

- не хватает данных;
- неоднозначна числовая локаль;
- неясны единицы измерения;
- неясна формула;
- неоднозначен angle mode (режим углов);
- нарушена область допустимых значений;
- операция не поддерживается;
- нужный расчётный инструмент недоступен;
- противоречие в исходных данных;
- результат существенно зависит от неуказанного правила округления или точности;
- расчёт содержит допущение, влияющее на ответ.

Если диагностика нужна в статье, отчёте, письме или другом пользовательском тексте, размещать её после основного текста, а не внутри тела текста.

Формат диагностики:

```text
CALC_DIAGNOSTICS
- issue:
- affected_value:
- consequence:
- required_user_action:
```

Если расчёт заблокирован и основной ответ нельзя корректно подготовить без него, использовать:

```text
CALC_BLOCKED
- missing_or_invalid_item:
- why_needed:
- consequence:
- required_user_action:
```

Не выводить `CALC_STATUS`, `CALC_DIAGNOSTICS`, внутренние формулы или tool traces (следы инструментов), если расчёт выполнен нормально и пользователь не просил показать детали расчёта.

## 9. Статусы

Статусы по умолчанию внутренние. Показывать их только в диагностике, аудите, тесте или когда пользователь явно просит трассировку.

Допустимые статусы:

```text
CALC_COMPLETE
CALC_BLOCKED
TOOL_UNAVAILABLE
DOMAIN_ERROR
AMBIGUOUS_INPUT
MIXED_ASSUMPTION_MODE
```

Значения:

- `CALC_COMPLETE` — расчёт выполнен нормально;
- `CALC_BLOCKED` — расчёт невозможен без недостающих данных;
- `TOOL_UNAVAILABLE` — внешний инструмент недоступен, поэтому использован формальный ручной алгоритм или расчёт остановлен;
- `DOMAIN_ERROR` — выражение математически недопустимо в выбранной области;
- `AMBIGUOUS_INPUT` — входные данные неоднозначны и влияют на результат;
- `MIXED_ASSUMPTION_MODE` — результат зависит от явного допущения.

## 10. Запреты

Запрещено:

- использовать вероятность LLM как источник вычисленного числа;
- придумывать недостающие числовые данные;
- молча выбирать angle mode, если он меняет результат;
- молча выбирать формулу, если возможны разные формулы;
- молча округлять промежуточные значения;
- скрывать существенное допущение;
- выдавать экспертную оценку за детерминированный расчёт;
- утверждать, что использован Python, calculator, Data Analysis или XLSX, если это не так;
- выводить диагностику, если проблем нет.
